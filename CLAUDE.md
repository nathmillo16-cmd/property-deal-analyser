What this project is

Deals N Yields is a UK property deal-analysis and deal-tracking web app for property sourcers and investors. A user signs up, enters headline figures from a listing across four strategies (BTL, HMO, Serviced Accommodation, or Flip), gets a full breakdown, a maximum bid to hit their target, and an optional AI verdict. Deals can be saved, promoted into a kanban pipeline to track through a sales process, and compared side by side. The app is a walled garden — signup/login is required before using anything — with a free tier and a paid tier (£29/month via Stripe) that unlocks the AI verdict, unlimited saved deals, and the pipeline.

Stack (as it actually is)

- Backend: Node.js / Express — server.js. Serves static HTML files, proxies AI requests to the Anthropic API (key stays server-side), and exposes all data endpoints (deals, pipeline, profile/defaults, Stripe checkout, Stripe webhook). Every data endpoint requires a valid Supabase bearer token; paid-only endpoints additionally check the caller's plan server-side via a shared fail-closed helper.
- Frontend: plain HTML/CSS/JS, no framework, no build step. Each page is a self-contained file (index.html, pipeline.html, saved-deals.html, home.html, portfolio.html, refurb.html, letters.html, login.html, landing.html, pricing.html) plus one small shared file, auth-guard.js, used by the logged-in pages to redirect to the landing page if there's no session.
- Auth/database: Supabase (Postgres + Auth), Row Level Security on every table, keyed to auth.uid().
- Payments: Stripe, test mode currently, live checkout + webhook flow both built and verified.
- Deployed on: Render, auto-deploying from the GitHub main branch (pushing to main ships to production — no separate deploy step).

THE MOST IMPORTANT RULE — calculation logic

The calculation logic for BTL, HMO, SA, and Flip has been verified line-by-line against the owner's own sourcing spreadsheets and worked examples. Do NOT change, "improve", refactor, or re-derive any calculation on your own initiative, and do NOT invent or guess a formula for a new strategy — the user supplies the exact spec. If you think a calculation is wrong, STOP and flag it to the user in plain English — do not silently alter it. Only change calculation logic when the user explicitly asks you to, and when you do, tell them exactly what you changed. When building a new calculation feature, verify it with a fully worked example (ideally by executing the real shipped code against known inputs, not just describing the formula) before telling the user it's done.

Verified calculation rules (do not alter without explicit instruction)

Shared/reused across strategies:
- Interest-only mortgage: Monthly = (loan × rate/100) / 12. This was the ONLY mortgage mode until repayment mode was added (see "Repayment mortgage mode" below) — a separate function, additive, this formula itself untouched.
- Deposit and purchase loan are calculated against PURCHASE PRICE (changed from EMV in the BRRR Part 1 work, see BRRR below). Only the BRRR refinance loan is on end value.
- Stamp duty: England and NI SDLT, additional property rates in force since 1 April 2025 (updated on the owner's explicit instruction, October 2026): 5% up to £125k, 7% £125k–£250k, 10% £250k–£925k, 15% £925k–£1.5m, 17% above £1.5m; under £40,000 no surcharge applies, so standard rates (0% at that price) are used. Rates live in STAMP_DUTY_CONFIG at the top of calc-engine.js, the one place to change them after a Budget. Verified: £100k = £5,000, £150k = £8,000, £200k = £11,500, £300k = £20,000. Old saved deals keep the stamp duty (and HMO/Flip totals) they were saved with. Reused as-is by every strategy. Stamp duty counts as cash needed to buy on EVERY strategy: it is included in total investment, money left in (mortgage, cash and BRRR), ROI and the ROI max-bid bisections (recomputed per candidate price). HMO and Flip always did this; BTL/BRRR and SA previously left it out (shown on screen only) and were changed to include it on the owner's explicit instruction on 2026-10-20, signed off by Nathan 2026-10-21. It never affects yields or cashflow. Old saved deals keep the figures they were saved with until re-run.

BTL:
- Mortgage loan = purchase price − deposit.
- Gross yield is on PURCHASE PRICE (btlData.gy), changed from EMV on the owner's explicit instruction, 2026-10-21, signed off by Nathan 2026-10-21. The EMV version is kept as btlData.gyEmv and shown alongside as "Gross yield (on end value)". Net yields (mortgage, repayment, cash, BRRR) stay on EMV and are labelled "on end value". Because gy feeds meetsYield, the verdict, deal cards, the compare table, the buy box min-yield check and the AI prompt, those all use yield on price for BTL now. Old saved deals keep their EMV-based gy until re-run. HMO and SA moved to the same convention later the same day (see their sections). Hand-check: £10,200 a year / £140,000 = 7.29% on price; / £200,000 = 5.10% on end value. The yield max bid (annual rent / target) was always a price-based formula, so it now matches gross yield exactly.
- Max bid = the MAXIMUM price to pay to hit target. Yield max bid = annual rent / target yield. ROI max bid solved by working back from target money-left-in.

HMO:
- Loan is deposit-derived from purchase price, same as BTL (the old flat 75% LTV of EMV was dropped in the BRRR Part 1 work).
- Bills auto-calculated at 10% of total rent.
- Searches count in both the mortgage and cash total investment and in the ROI max-bid bisections (the mortgage total used to leave them out while the cash total included them; fixed on the owner's explicit instruction, 2026-10-20, signed off by Nathan 2026-10-21).
- Council tax entered annually, divided by 12 for monthly display.
- Gross yield on purchase price (hmoData.gy), with the EMV version as hmoData.gyEmv shown "on end value"; net yields on EMV. Moved from EMV on the owner's explicit instruction, 2026-10-21, signed off by Nathan 2026-10-21. Hand-check (default HMO): £1,800 x 12 = £21,600 / £140,000 = 15.43% on price, / £200,000 = 10.80% on end value. ROI max bid uses an 80-iteration bisection search (stamp duty is banded/non-linear, so no closed form).

Voids, letting fee and safety certificates (BTL, BRRR and HMO; not SA or Flip). Added on the owner's explicit instruction, 2026-10-21, signed off by Nathan 2026-10-21:
- Voids % comes off the monthly rent (BTL: b-rent; HMO: the room total) for the net figures only: management % and maintenance % are worked on the rent after voids, and so are cashflow, net yield, ROI and the ROI max bids. Gross yield, the yield max bid, HMO bills (10%) and the lender check (ICR) stay on the full rent (owner's instruction, 2026-10-21). btlData.rent and hmoData.totalRent are still the full rent, with rentAfterVoids and voidLossYearly saved alongside.
- Letting fee £ and safety certificates £ are yearly costs, taken off monthly as (fee + certificates) / 12 in every cashflow (interest-only, repayment, cash, BRRR) and in the max-bid bisections. Not upfront costs, so total investment is unchanged.
- All three default to 0 (a deal saved before this reopens with 0, never the user's Settings defaults), so every figure is identical when they're 0: verified against 56 BTL and 60 HMO saved fields and 88 on-screen values. Each set item shows as its own line in the Full breakdown (b-rc / h-rc).
- Worked example (default £140k / £200k EMV / £850 BTL with deposit 20%, rate 5%, insurance £40, management 8%, maintenance 5%, solicitor £1,500, searches £300, mortgage fees £1,495, plus 4% voids, £300 letting fee, £200 certificates): rent after voids £816/mo (£9,792 a year, £408 voids); cashflow 9,792 - 480 - 783.36 - 489.60 - 300 - 200 - 5,600 = £1,939 a year (was £2,794); ROI 1,939 / 48,595 = 3.99%; net yield 1,939 / 200,000 = 0.97%; gross yield stays 10,200 / 140,000 = 7.29% on price; yield max bid at 8% = 10,200 / 0.08 = £127,500.

SA (Serviced Accommodation):
- Revenue = nightly rate × (occupancy% / 100) × 365.
- Running costs: management/utilities/maintenance as % of revenue (each defaults to 10%, user-editable), plus fixed cleaning and insurance (£/mo × 12), plus council tax (annual, as entered).
- Net annual income (before mortgage) = revenue − running costs.
- Cashflow: net income minus annual mortgage interest (mortgage version); net income as-is (cash version).
- Gross yield on purchase price (saData.gy), EMV version as saData.gyEmv shown "on end value"; net yield on EMV. Moved from EMV on the owner's explicit instruction, 2026-10-21, signed off by Nathan 2026-10-21. Hand-check (default SA): £35,588 revenue / £200,000 = 17.79% on price, / £240,000 = 14.83% on end value.
- Total cash invested reuses BTL's exact pattern (deposit/purchase-price-based), extended with SA's own upfront costs.
- Max bid uses BTL's closed-form approach (not HMO's bisection).

Flip (buy-refurbish-sell):
- Cash-only — no mortgage version, no rental income, no yield concept.
- Total cash invested = purchase price + stamp duty + buying fees + refurb + contingency amount. Estate agent fee is deliberately excluded from cash invested (it comes out of sale proceeds, not paid upfront).
- Contingency is optional (% of refurb cost); blank is treated as 0.
- Net profit = sale value − purchase price − stamp duty − buying fees − refurb − contingency amount − estate agent fee amount.
- ROI = net profit / total cash invested. Profit margin = net profit / sale value.
- Max bid solves for the highest purchase price still hitting a target ROI via 80-iteration bisection (purchase price affects stamp duty, which affects both sides of the ROI calc). The search direction was independently verified numerically (ROI strictly decreases as purchase price rises) rather than assumed from HMO's own search. The estate agent fee is fixed to the (fixed) sale value throughout the search, not recalculated per candidate price — deliberate, per the owner's explicit instruction on how a flipper actually reasons about a deal.

Repayment mortgage mode (built, committed a2ba749): BTL/HMO/SA (not Flip — Flip has no mortgage at all) now also compute a REPAYMENT-mortgage scenario alongside the original interest-only and cash scenarios. `mortRepay(loan,rate,termYears)` is a new function, additive alongside the existing interest-only `mort()` — standard amortisation formula, 0%-rate edge case handled explicitly (loan ÷ months, no divide-by-zero). Option A, an explicit product decision: the whole repayment monthly payment is treated as a cost, same as interest-only's payment — no capital/interest split, no equity treatment. Every downstream cashflow/yield/ROI/max-bid figure for repayment mode reuses the exact same formula shape interest-only already used, just fed the repayment payment instead of the interest-only one — mirrors the mortgage-vs-cash pattern each strategy already had, extended to a third mode. A mortgage term input (years, default 25) feeds this and exists on all three strategies' input forms.

BRRR (built, two-part session): Part 1 switched BTL, HMO and SA's deposit and loan to derive from PURCHASE PRICE instead of EMV — they used to deposit/loan against end value, which was really a refinance calculation happening in the wrong place, since a purchase lender lends against the price paid, not the end value; this fixed a real bug where a below-value deal (price well under EMV) could borrow more than the purchase price itself. HMO's flat 75% LTV of EMV was dropped entirely in favour of the same deposit-derived loan BTL/SA already used. Max bid (`oR`/`roR`) moved from closed-form algebra to bisection on BTL and SA, matching HMO/Flip's existing proven pattern, since loan (and so the mortgage payment) now depends on the very price being solved for; HMO's own bisection was fixed to recompute the mortgage payment per candidate price too, not just stamp duty, which also fixed max-bid searches that were silently pinned to the search floor for some genuinely profitable deals.

Part 2 added BRRR as a fourth financing tab on BTL, HMO and SA (not Flip — no rental income or holding period to refinance against), alongside Interest-only/Repayment/Cash: refinance at a chosen LTV of end value, interest-only or repayment, rate and term reusing the existing mortgage inputs. Money left in = full cost minus the refinance loan; cashflow and ROI include the refinance mortgage payment. Originally built as a Cash-tab toggle, then restructured into its own tab (same calculations, just relocated) since users think of BRRR as a distinct financing route to compare against the others, not a modifier on top of Cash. The Cash tab itself is unaffected, pure cash-and-hold, exactly as before either part of this work. Mortgage tabs (interest-only and repayment) are straight purchases and never refinance, on any strategy, including HMO — a mortgage-tab deal is "buy with a mortgage and keep it," full stop; an HMO buyer who actually purchases with cash or bridging finance and then refinances models that entirely via the BRRR tab, exactly like every other strategy.

Side effect, not a bug: for BTL and SA, "money left in deal" became algebraically identical to "total investment" on the mortgage tabs once loan was price-derived (the price terms cancel out), and the same now holds for HMO too — so on all three strategies' interest-only and repayment tabs, the "Total investment" card was relabelled "Total initial investment" and the "Money left in deal" card was hidden entirely (redundant with Total investment). Money left in only appears where it's actually meaningful: the Cash tab (trivially equal to total investment, since nothing is borrowed) and the BRRR tab (genuinely reduced by the refinance loan) — it's the only place cash actually comes back out of the deal. Labels/footnotes/AI-verdict prompts/Settings' Investment Defaults field were all updated from "of EMV" to "of purchase price" to match the Part 1 change.

Known limitation, worth a future enhancement: the BRRR tab shows the position AFTER refinancing only — a snapshot, not a timeline. The refurb period itself (the gap between buying and refinancing), any bridging/short-term finance cost during that period, and the time it actually takes to refinance are none of them modelled. A user reads the BRRR tab as "day one after refinance completes," not as a full project cashflow from purchase through to refinance.

Verified via a real runtime harness (not just described): interest-only and cash outputs are byte-identical before/after this change, across every pre-existing key in each strategy's saved data object; the amortisation function matches the standard mortgage-calculator figure (£150,000 loan / 5% / 25yr ≈ £876.89/mo); and the max-bid reverse-calc is self-consistent for all three modes across all three strategies (the computed max bid, plugged back in as the purchase price, reproduces the target ROI exactly).

That self-consistency check also caught two PRE-EXISTING max-bid bugs, unrelated to the repayment work itself, found and fixed in the same session with explicit sign-off (not previously known — no prior worked-example check had exercised max-bid this way): HMO's `oR` bisection had its comparison direction inverted for what is actually a strictly decreasing function (ROI vs. candidate price) — it was converging to the wrong region of the search space entirely, not just imprecisely. SA's `oR` was missing a `-dep` (deposit) term in its algebra — `mROI` is computed against `mTI`, which includes `dep` as its own additive term, but the max-bid formula (the algebraic inverse of that) hadn't been subtracting it back out. Both are now fixed and verified self-consistent for interest-only AND repayment. BTL's `oR` was already correct throughout (it's derived from `mMLI`, not `mTI`, so no `dep` term was ever needed) and required no change.

Payback and all money out (owner's go-ahead, 2026-10-29; checked by Claude against standard cash-on-cash and payback definitions, not the owner's spreadsheet, at his request). Two display/logic bugs: (1) payback was shown for loss-making deals because the minus sign was dropped (Math.abs), e.g. a BTL losing £2,595 a year showed "18.61 yrs"; (2) a BRRR deal with all money out (money left in £0 or less) showed a negative ROI (e.g. -13.05% on £2,376 a year cashflow with £18,200 out), failed the ROI target and showed a payback. Now: `paybackYears(cashIn, yearlyCF)` in calc-engine.js gives null when cashflow is £0 or less (shown "Never", or "N/A" when nothing is in the deal either), 0 when cash in is £0 or less and cashflow positive (shown "Instant"), else cash in / yearly cashflow. Saved mPB/cPB/rPB/bbPB are that value (null = never). BRRR ROI (`brrrRoi`, bbROI on BTL/HMO/SA) is null when money left in is £0 or less, shown "All money out" (green if cashflow after refinance is positive, red if not), and meetsROIBRRR is then true only if that cashflow is positive. compare-deals.js `fmtCompareField(f, v, d)` shows "All money out" for bbROI whenever d.bbMLI <= 0, so older deals saved with a negative bbROI read correctly too. deal-verdict.js, the buy box and deal-planning.js already treated money left in <= 0 as all out. The AI prompt says "never" for a null payback. Verified: old vs new engine on 9,000 random BTL/HMO/SA deals (1.4m checks): the only saved fields that changed were the payback fields, bbROI and meetsROIBRRR, and only on loss-making or all-money-out deals; every profitable deal's payback is identical; the full independent maths check still gives 0 mismatches.

Max-bid check (owner's sign-off, 2026-10-22, every ROI max bid: BTL/HMO/SA interest-only `oR` and repayment `rOR`, and Flip `oR`): stamp duty jumps from £0 to £2,000 at £40,000, and the bisection used to land on exactly £40,000 when the true answer was £39,999 (at £40,000 the ROI falls well short of target). `bidMeetingTarget()` (calc-engine.js, next to `mort()`) now checks the whole-pound result actually meets the target to 2 decimal places (`roi >= target - 0.005`) and, only if it doesn't, steps it down £1 at a time until it does. Each bisection's ROI formula moved into a local `roiAt(price)` used by both the search and the check, arithmetic unchanged. Verified on 400 random deals (84,000 saved figures): the only differences from the previous engine were 43 max bids going from £40,000 to £39,999, and every one of 2,294 achievable max bids now meets its target when plugged back in (the old engine missed on exactly those 43). Worked example: BTL £60k end value, £474 rent, 15% target: £40,000 gives 13.77% ROI, £39,999 gives 15.02%, max bid now £39,999.

BRRR max bid for the target ROI (owner's sign-off, 2026-10-22; `bbOR` on btlData, hmoData and saData): the highest price where cashflow after refinance / money left in after refinance reaches the target ROI, with all money out counting as reaching it. Cashflow after refinance doesn't depend on price (rent and refinance loan are both end-value based), so it is the highest price where money left in <= yearly cashflow after refinance / target; bisection on money left in (which only rises with price), `Math.floor` so the result always meets target. 0 (not achievable) when cashflow after refinance is £0 or less. Uses the same target ROI as the other tabs, no new input. Shown as "To achieve X% ROI (BRRR, after refinance)" under Recommended offer prices: on the BRRR strategy tab (BTL panel in brrr-mode, `.brrr-only`, hidden on plain BTL) and always on HMO and SA. Separate from, and higher than, deal-insights.js's existing "Max bid to get all your money out". When not achievable, `brrrBidReason()` (index.html) says why in one line: "Not achievable. You would lose £X a month after refinancing." when cashflow after refinance is negative, "No cashflow after refinancing." at £0, otherwise "Not achievable at this target. Try a lower target ROI." Example on Nathan's own defaults (6% rate, 75% refinance, 5.9% target, default £140k/£200k/£850 deal): £10,200 rent - £1,620 costs - £9,000 refinance interest = -£420 a year, so not achievable; at 5% it is £148,322. Like the other max bids, the "Make it realistic" bridge cost is fixed at the asking price. Worked example (default BTL): £140k price, £200k end value, £850 rent, 75% refinance = £150k loan, cashflow after refinance £2,580 a year; at 15% you can leave in up to £17,200, so max bid £147,290 (money left in exactly £17,200 = 15.00%); money-out bid £131,215. Default HMO £184,907, default SA (20% target) £184,328. Verified on 822 achievable random cases: every bid meets target and £2 more doesn't.

AI verdict

One verdict per strategy (BTL, HMO, SA, or Flip), each with its own tailored prompt. Sections in order: VERDICT, RISK FLAGS, STRATEGY FIT, WHAT NEEDS TO CHANGE. Triggered by a button (not automatic), gated to paid users only, capped at 50 analyses per calendar month per user, logged only on a successful Anthropic response (a failed call doesn't count against the cap).

Auth flow

Supabase email + password (not magic-link). Sign up → "check your email to confirm" message shown, user is NOT dropped into the app before confirming. If a login attempt fails specifically because the email isn't confirmed (Supabase's error.code === 'email_not_confirmed'), a "Resend confirmation email" option appears — resend only ever fires in response to that specific failure, never as a standalone/blind form, to avoid enabling spam to arbitrary addresses. Forgot-password flow: request email → Supabase's recovery link (implicit flow, tokens in a URL hash) → the app detects the PASSWORD_RECOVERY auth event and shows a set-new-password panel → success signs the user into the app directly (no second login needed). Confirmed working against the real Supabase project, not assumed. Logout is available from every logged-in page and returns to the landing page.

Saved deals

`deals` table (id, user_id, deal_type text — 'btl'/'hmo'/'sa'/'flip', deal_data jsonb, created_at, pipeline_stage text nullable). JSONB + deal_type means new strategies slot in with no schema change (already proven twice, for SA and Flip). Write path is browser → server → Supabase, never browser → Supabase directly, so validation and usage caps live in one place. RLS restricts every row to its own user_id. Free users are capped at 2 saved deals; paid users unlimited — enforced server-side.

Dead-schema note, important: `deals` also has a nullable `address` column (migration run directly in Supabase this session) that is NOT currently written to anywhere. A separate, optional address input was built alongside the save flow, then deliberately reverted in favour of a single combined field (see the save-modal note below) — the column was deliberately left in place rather than dropped, as the intended home for a real structured-address field later (see "structured property address with autocomplete" in Feature ideas below). Don't assume this column holds data — every row's `address` is null.

Deal Workspace (built, saved-deals.html): clicking a saved-deal row opens a modal — index.html's save modal and saved-deals.html's own Move to portfolio modal were the first two modals on this app; this is the third, on saved-deals.html. An **Analysis** section is always free — it reuses compare-deals.js's own `COMPARE_FIELDS`/`fmtCompareField` (the same per-strategy field list and formatter the compare table already uses) rendered as a plain label/value list rather than a comparison table, since it's one deal, not several. Below it, three sections are paid-gated, each independently: **Notes**, **Offer history**, and **Stage**. Notes/offers markup, CSS, and JS (`loadNotes`/`addNote`/`deleteNote`, `loadOffers`/`addOffer`/`updateOfferOutcome`/`deleteOffer`, the `.dd` outcome dropdown + its `handleOfferOutcomeChange` bridge) were copied from pipeline.html's existing details modal essentially verbatim, retargeted from that modal's `detailsDealId` to this one's own `workspaceDealId`, and hit the exact same endpoints (`/api/deals/:dealId/notes`, `/api/notes/:id`, `/api/deals/:dealId/offers`, `/api/offers/:id`) — no new backend work. Stage shows a 5-option dropdown (`POST /api/pipeline/:id/stage`) if the deal is already pipelined, or a single "Add to pipeline" action (`POST /api/pipeline`, same endpoint the row's pre-existing button already used) if it isn't yet; either way it calls `loadSavedDeals()` afterward so the row's own pipeline badge and the modal's own control both refresh in sync.

Plan-gating for this: saved-deals.html previously had no plan awareness at all (it's a free page). It now fetches `GET /api/profile` on load and stores `currentPlan`, purely to decide what these three sections render — the page itself stays otherwise ungated. This is a **new gating shape** for the app: a partial lock *within* one view (three sections behind one plan check, inside an otherwise-free modal), rather than the all-or-nothing whole-page lock every other paid page (pipeline/portfolio/refurb/letters) uses. A free user never fires the notes/offers/pipeline requests at all — gated client-side before any fetch, not just hidden after a 403.

Deal Workspace Phase 1 (built, a later session): supersedes the separate **Notes**/**Offer history** sections described in the Deal Workspace paragraph above, which no longer exist — `loadNotes`/`addNote`/`deleteNote`/`loadOffers`/`addOffer`/`updateOfferOutcome`/`deleteOffer` were removed from saved-deals.html entirely (pipeline.html's own, separate copy of that same functionality is untouched, see below). First diagnosis (since corrected below) blamed Row Level Security on `profiles` not scoping `SELECT` to the caller's own row at all — a real authenticated query appeared to return every row in the table (6 rows for a single-user query). Actual root cause, confirmed once properly isolated: RLS on `profiles` was never fully open — the real, additive `role`-based policy from `db/021_profiles_role.sql` (superusers can see every row, for the CRM's owner dropdown — see the Admin/CRM section) meant a SUPERUSER's own RLS-scoped query legitimately returns multiple rows, by design. Several of this app's `profiles` queries (`GET /api/profile`, `getUserPlan()`, `getUserRole()`) called `.single()` (which requires exactly one row) without an explicit `.eq('user_id', ...)` filter, relying on RLS to implicitly narrow the result to one row — true for every normal user, but false for a superuser. The unfiltered `.single()` against multiple rows threw `PGRST116` ("Cannot coerce the result to a single JSON object"), silently swallowed into the endpoint's generic free/user fallback — so a superuser's own plan/role stopped loading correctly the moment the superuser policy started actually working, while every normal (non-superuser) account was unaffected throughout. Fix, both parts verified: (1) application code — commit `be60008` ("Add CRM system, tier automation, weekly digest, Stripe integration, investment defaults") added an explicit `.eq('user_id', userId)` to every `profiles` read in `GET /api/profile`; `getUserPlan()`/`getUserRole()` already had it. (2) database — the `profiles` RLS policies were checked directly in the Supabase dashboard and confirmed correct: `auth.uid() = user_id` for normal own-row access, plus the additive superuser-sees-all policy via the `is_superuser()` helper (recursion-safe, per `db/028_fix_superuser_recursive_policy.sql`). No remaining security gap — a normal user's RLS-scoped query was never actually returning other users' rows; only a superuser's own account was ever affected, and only as a display bug (plan/role failing to load), not a data-exposure one.

Comps engine (built)

Server-side sold-price valuation and post-refurb GDV estimation, on its own tab in the calculator. Paid-gated the same way as the Pipeline and AI verdict — auth + plan checked server-side in POST /api/comps, and the EPC API key never reaches the browser (it lives entirely inside epc-floor-area.js). The old `postcodes` table was dropped entirely as part of a re-architecture — at 534MB it was breaching the Supabase free tier's disk allowance and had actually forced the database into read-only mode, so this was a forced fix, not a preference. The subject postcode is now resolved live, per request, via a single call to postcodes.io (postcodes-io.js, free, no API key) — including terminated postcodes (real, retired postcodes with no live geography of their own): postcodes.io's 404 response for one still carries its last-known coordinates, which lookupPostcode() returns directly rather than treating as a failure, and if an MSOA is separately needed for a terminated postcode (the crime feature, below), a reverse-geocode fallback finds the nearest live postcode's MSOA instead of hard-failing. The 0.5-mile radius search then runs directly against HM Land Registry Price Paid Data (PPD) sold prices in `sold_prices`, which carries its own lat/lng columns (db/012_sold_prices_lat_lng.sql), filtered with the same bounding-box pre-filter + exact haversine check the old postcode-table lookup used, just applied to sold_prices directly instead of joining through a list of nearby postcode strings. Historical rows were geocoded once via scripts/backfill-sold-prices-lat-lng.js (bulk postcodes.io lookups, ~408k distinct postcodes); scripts/ingest-sold-prices.js now geocodes every newly-ingested batch inline the same way, so a future PPD import doesn't need a separate backfill pass to become comps-eligible. Each comp is enriched with EPC floor area (exact house-number match; permanent cache in epc_floor_area_cache, including cached "no match found" results, so any given postcode's EPC data is only ever fetched once). Headline valuation is the median sold price, with a 20th/80th percentile range (null below 5 comps — not enough evidence for a range) and a high/medium/low confidence signal based on comp count only (see open items below). A GDV tier picker (50th/75th/90th percentile of floor-area-matched £/sqm comps — conservative/refurbished/best-in-area) lets a sourcer enter a post-refurb floor area and apply the resulting GDV as the end value (EMV, or Sale Value for Flip) on any of the four strategy tabs, via an explicit "Use this GDV" button — never silently auto-filled.

Your own comparables (built 2026-10-29, owner's request; db/061 run in Supabase the same day): my-comps.js, shared by the calculator's Comps tab (index.html, a "Your comparables" section between the comps summary and Crime, shown even before comps are run) and the Comps dropdown on the deal page (saved-deals.html). Lists every sale our engine found in a closed dropdown ("See the N sales"); each of ours can be removed (with Undo) and the user can add their own (address, price, Sold / Sold STC / For sale, date, beds, sqm, link, note; tagged "Yours"). Our figures are never changed: our summary is labelled "Our comps", and once anything is removed or added a separate "Your comps" box shows the median price and median price per sqm of what's left plus theirs, using the same percentile maths as get-comps.js, with one "Use as end value" button in the calculator (owner chose showing both). Stored as deals.user_comps { excluded: [address|date|price keys], added: [...] }: sent with POST /api/deals (user_comps, paid only, separate failure-tolerant update after the insert), edited later via POST /api/deals/:id/user-comps (paid, cleanUserComps validates; links must be http(s)), read back by attachUserComps on the deal lists. Crime feature (Stages 1-4, built)

Per-1,000-residents crime rate shown on the Comps results, sourced from Police UK's open bulk data (a June 2026 monthly export) rather than their live per-call API. Four tables: `msoa_population` (ONS mid-2024 population estimates, needed to convert raw incident counts into a per-capita rate), `msoa_crime_rate` + `crime_benchmark_meta` (rate per 1,000, low/medium/high band, national percentile), and `msoa_crime_breakdown` (Stage 4 — 6 grouped categories: violence, ASB, shoplifting, burglary, vehicle, other), all computed by scripts/compute-crime-benchmark.js in the same pass and re-run whenever the underlying police data refreshes — not live per-request. The MSOA for a subject postcode resolves via the same postcodes.io lookup the comps engine uses (see above), including the terminated-postcode reverse-geocode fallback — no separate stored geography column. Percentile is the headline figure (a band alone is too coarse — a moderately-high and a very-high area both read as "High"); band and raw rate are shown as secondary detail. Validated against known Nottingham areas before shipping, not just spot-checked against the formula.

Known limitation: the per-capita rate reads town-centre and retail-heavy MSOAs higher, because recorded crime (shoplifting, ASB) concentrates where people gather, not where they live. This is standard behavior for the metric and matches how professional crime-stats sites present the same data — not a bug in this app's calculation. The caveat text shown alongside the crime figure explains this rather than hiding it.

Stage 4 (crime-type breakdown) makes that caveat checkable instead of just asserted: an expandable section under the crime box, collapsed by default, showing all 6 groups percentage-primary ("Anti-social behaviour — 62% (106)") ordered descending. Validated against Beeston High Street (E02005860) — shoplifting-led, confirming this is what explains that area's high headline percentile, not violence.

Employment feature (built): a fourth Comps-results area block, below crime and planning constraints — council-wide employment rate (ONS Nomis, dataset NM_17_5, Annual Population Survey, "Employment rate - aged 16-64") plus the top 5 industries by share of local employment (ONS Nomis, dataset NM_189_1, Business Register and Employment Survey, 18 broad SIC-2007 sections; the dataset's own built-in percentage measure returned empty in live testing, so percentages are computed server-side from raw counts instead). Both datasets confirmed live and genuinely keyless — verified with real numbers for Nottingham, Broxtowe, and Westminster, not assumed (a fresh, independent re-check specifically ruled out NM_57_1, which turned out to be "jobs density," a different metric with no industry dimension at all). Geography: postcode → LAD code (postcodes.io's admin_district code, e.g. "E07000172" — lookupPostcode() in postcodes-io.js now returns this as adminDistrictCode, additive alongside the existing adminDistrict name) → a small server-side proxy, nomis-employment.js, which resolves that GSS code to Nomis's own internal geography id (a ~317-row local-authority list, cached in memory since it barely changes) and queries both datasets. Figures are explicitly labelled as local-authority-wide, not street-level ("Employment · [council] · council-wide figures" + a "figures for the whole local authority, not the immediate area" caveat line) — same honesty pattern as the crime feature's own town-centre-bias caveat. Persisted to draft exactly like crime/planning (lastEmploymentResult, restored without re-firing the network call) — not a special case. Degrades gracefully via Promise.allSettled — a Nomis outage never breaks the rest of the Comps tab, same isolation pattern as crime/planning.

A poisoned-cache bug was found and fixed during dedicated failure-path testing (a later, separate session): the in-memory LAD-geography cache in nomis-employment.js only checked whether a promise existed, not whether it had succeeded — so a single failed fetch (an outage, a timeout) got cached as if it were a completed lookup, silently disabling employment data for every user for the rest of the server process's life, with no recovery short of a restart. Timed proof of the bug (0ms responses on the 2nd/3rd calls after a real 82ms first failure, meaning no retry was even attempted) and of the fix (a subsequent call after "recovery" took a real 1605ms and succeeded, with later calls dropping back to ~336ms once genuinely cached) are both in the session, not just asserted. Fix: only a successful load is cached; a rejection clears the cache variable so the next call retries fresh.

Named employers (e.g. "the biggest employer here is Boots") were investigated and deliberately NOT built — legally unavailable for free, not just hard to find. The underlying business register (IDBR) is protected under the Statistics of Trade Act 1947; ONS is barred from publishing individual business names/data without that business's consent. This is a hard legal barrier, not a temporary data gap — confirmed via the Act itself, not inferred from an absence of search results. The closest free alternative (and what's actually built) is industry-by-sector share, which needs no company names.

- Selective licensing flag: softened from parked (2026-08-04 correction) — two new findings since the "NOT on planning.data.gov.uk" note above. Consolidation note (2026-08-04): several of these same commercial APIs (Homedata, Street Data, PropertyData) bundle council tax band together with EPC, floor area, price history, and comparable sales in a single per-address call — so council tax band, rental comparables (see "Buy, don't build" below), and richer property data might end up being one purchase rather than three separate ones. This is a live, free, official, address-level feed — the earlier "not a live property feed" verdict was wrong. Buy, don't build:
- Rental comparables: PropertyData's "quoting rent" is a proprietary dataset built from VOA 2026 rateable values plus MHCLG floor areas, reconciled and market-adjusted — not a technique we're missing, a licensed commercial data product. The real choice is buy their API, or license the same VOA/MHCLG feeds and build the reconciliation ourselves; buying is the sane option.
- Structured property address with autocomplete (2026-08-10): researched for the deals save flow. postcodes.io — the free API this app already leans on for comps/crime/planning — CANNOT do address-level type-ahead; its own autocomplete endpoint only completes postcode strings, not street addresses (it's built on postcode-centroid data, not a premises-level dataset like Royal Mail's PAF). getAddress.io, a former free-ish option, shut down 4 Feb 2026 after losing a High Court database-rights case to Ideal Postcodes/Royal Mail — not usable. Best path if this is ever pursued: Ideal Postcodes (the same team that maintains open-source postcodes.io) — pay-as-you-go, ~2p per completed lookup, free while the user is still typing (a credit is only spent once a full address is picked), no subscription, so no surprise recurring bill. Deliberately NOT built pre-launch — it would be the app's first paid third-party dependency, for what's only an optional convenience field. `deals.address` (see the dead-schema note above) is already sitting ready as the column this would write to.

Researched, no clean data source found — park unless one emerges:
- Auction-unsold finder: corrected (2026-08-04) — EIG (Essential Information Group) is a central database of every UK auction result since 1991, including a dedicated unsold-lots aggregation, so the data does exist centrally (the earlier "not published centrally anywhere" verdict was wrong on that specific point). Verdict: central source exists, commercial, API access unconfirmed — needs verification before this is a real build, not yet buildable.

The national MHCLG Council Taxbase dataset gives long-term-empty counts per local authority only (no addresses, not useful for finding a specific property). However, some individual councils publish address/division-level empty-property data on data.gov.uk (e.g. Northumberland, by electoral division, with length-of-time-empty and council tax band). So: no national address-level feed, but possibly buildable in specific council areas that publish granular data — the same patchy, per-council shape as the Article 4 coverage situation (see Planning constraints panel above).
- Major employers (area research/stats, 2026-08-04, confirmed harder 2026-08-12): park — and not just "no source found." Nomis (see Employment feature above) gives employment by sector and count, never company names. Confirmed why: the underlying business register (IDBR) is legally protected under the Statistics of Trade Act 1947 — ONS cannot publish individual business names/data without that business's own consent. A structural legal barrier, not a gap that might close later. Companies House was also checked and doesn't collect employee-count data at all. How to work with me (the user)

- The user is new to code. Explain what you're about to do in plain English before doing it, and after making changes, say what you changed and why.
- Claude sessions on claude.ai (since 21 Oct 2026) don't push to main: they push a `claude/...` branch and open a pull request, and Nathan signs off before it's merged. Anything touching calc-engine.js waits for his check against his spreadsheets.
- WORKFLOW: work directly on main, no branches. Always `git pull --ff-only origin main` before starting and again before pushing. Pushing main deploys live on Render. Nathan also pushes to main: if a pull or merge conflicts, stop and explain it in plain English before changing anything. Stage files explicitly so unrelated uncommitted work never sneaks into a commit.
- Make one focused change at a time; don't refactor broadly or rename things unprompted.
- Don't touch the calculation logic (see above), and don't invent/guess a formula for a new feature — ask for the exact spec.
- Before anything is pushed to the shared GitHub repo, verify .env is still git-ignored and scan the diff for secrets — flag anything key-related rather than assuming it's handled.
- When adding a new calculation-bearing feature, verify byte-for-byte that existing verified calculation functions are untouched (diff/checksum before and after), and give a fully worked example before considering it done.
- COPY STANDARD: no em-dashes (—) in user-facing text anywhere in the app — labels, headings, messages, warnings, empty states, PDF/letter copy, tooltips. They read as AI-written. A full app-wide sweep removed every one that had crept in (reworded with normal punctuation — comma, full stop, colon, or a restructured sentence — never just swapped for a hyphen, which looks just as off). Going forward, any new user-facing copy should be written clean of them from the start rather than needing another sweep later. This rule is about what's shown to users, not about this file's own prose or code comments, which are unaffected.
- After pulling (or after any session pulls/rebases for you), restart the local `node server.js` process before testing. A running server keeps serving whatever server.js it loaded at startup — a `git pull` alone doesn't reload it, so behaviour can look broken or stale when it's actually just running old code. Found the hard way: the paid-status bug (see the profiles RLS note above) appeared to still be present locally purely because the server hadn't been restarted after the fix landed.
